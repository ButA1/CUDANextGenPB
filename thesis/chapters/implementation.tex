\section{Enabling CUDA}
\label{sec:implementation-enabling-cuda}

This project is built using a good old Makefile, with operating system specific settings loaded in called the \texttt{local\_settings.mk}.
The flags in the \texttt{local\_settings.mk} take precedent over those in the Makefile.
It is compiled using the \texttt{mpicxx} compiler, so I would need to employ the same strategy as shown in the RWTH tutorial \cite{rwth_cuda}.

As a first step, I added CUDA compilation target in the Makefile to compile CUDA source files with \texttt{nvcc}.
Next I added the \texttt{-dlink} flag to resolve CUDA runtime symbols between CUDA and non-CUDA object files.
This creates a intermediate object file \texttt{device\_link.o}
To make \texttt{nvcc} compile header files, I included \texttt{CPPFLAGS} and MPI's internal flags by reading them from the shell using \texttt{shell \$(CXX) --showme:compile}.
I then switched to the \texttt{local\_settings.mk} files where I added CUDA library flags and the \texttt{rpath} to \texttt{LDFLAGS}, as well as \texttt{-lcudart} to LIBS.
Finally I passed all CUDA object files, including \texttt{device\_link.o} to \texttt{mpicxx}.

\section{Linear Equation Solver}
\label{sec:implementation-lin-eq-solver}

I chose to implement AMGX over cuDSS due to high memory usage of the latter.
Since AMGX is not part of the standard CUDA toolchain, the \texttt{LDFLAGS} of \texttt{local\_settings.mk} needed to be updated with \texttt{-lamgxsh} and the \texttt{rpath}.
Since NGPB already has a choice between two linear solvers, I simply added AMGX as an option to the \texttt{linear\_solver} parameter in PRM file.
Settings for LIS are inserted directly into the file.
This was not a good option for AMGX as its configuration can be quite big, so to allow for arbitrary configurations to be loaded, the new \texttt{amgx\_config} parameter, which takes the path to a AMGX configuration.
The call structure mirrors the other solvers as well, plugging in next to \texttt{lis\_\allowbreak{}compute\_\allowbreak{}electric\_\allowbreak{}potential} and \texttt{mumps\_\allowbreak{}compute\_\allowbreak{}electric\_\allowbreak{}potential} simply as \texttt{amgx\_\allowbreak{}compute\_\allowbreak{}electric\_\allowbreak{}potential} in the code base.

\subsection{sparse\_matrix\_template}
\label{sec:implementation-bimpp-sparse-matrix-template}

BIMPP stores both local and non-local values of the distributed sparse matrix in a \texttt{std::vector} of \texttt{std::map<int, double>}.
In \texttt{x86\_64} \texttt{libstdc++}, \texttt{std::map} is implemented using a red-black tree, whose node is comprised of 3 pointers, a color enum, and a \texttt{std::pair}.
The three pointers exist for the parent, left and right at take up 24 Bytes.
The color enum, including padding takes up 8 Bytes.
In the context of the distributed sparse matrix, the \texttt{std::pair} is a tuple of type \texttt{<int const, double>}.
So 4 Bytes for the integer, plus 4 Bytes for padding and 8 Bytes for the double comes out to 16 Bytes.
All together this totals 48 Bytes.

In comes \texttt{flat\_map} from the already reference \texttt{boost} library.
It is a vector based implementation rather than a tree based one.
Its memory footprint is just 24 B, essentially half.
This change is also minimally invasive, only changing an underlying data type in the \texttt{sparse\_matrix\_template} of BIMPP.

This does not solve the issue of the global row being replicated on each rank.
For this a more sophisticated communication patter needs to be used, as was demonstrated in the SHIRO paper \cite{zhuang2025shiro}.

\subsection{bim3a\_solution\_with\_ghosts}
\label{sec:implementation-bimpp-bim3a-solution-with-ghosts}

As explained before in \ref{sec:nextgenpb-libraries-bimpp-bim3a-solution-with-ghosts}, this function is used throughout NGPB because it handles the exchange of non-local- and ghost values through a lot of expensive calculations.
First it updates every quadrant and its neighbors with \texttt{quadrant\_t::update()} hidden inside \texttt{quadrant\_iterator::operator++()}, without skipping those that have been already updated as the neighbor.
This also computes the physical vertex positions through \texttt{p8est\_qcoord\_to\_vertex}, which go completely unused.

Turns out, this is not necessary at all. 
\texttt{p4est} already stores this information.
All I did is reuse it.
To get all the non-owned nodes reference by the local ones, I referenced \texttt{lnodes->nonlocal\_nodes}.
For the ghost layer quadrants, I iterated through \texttt{tmesh\_3d::ghost\_data}, which is always 40 entries long per ghost.
This drastically reduces the runtime at multiple points in the code.

\section{Energy Calculation}
\label{sec:implementation-energy-calculation}

Since ray cache is relatively hard to port to the GPU, I decided to go for a simpler route:
Keep the classification, flux and normal calculation on the CPU.
They are essentially just lookups on the ray cache, which take very little time.
Reformulating them was not worth it. 
Besides, the true weight of the computational effort lies in the pairwise interactions themselves.
Thus the idea was to collect the necessary data into flat arrays, to then do execute those on the GPU.
At the end, I settled on 3 implementations, each being a viable option in different scenarios.
The naive implementation or kernels are surprisingly useful on workstation GPUs, which are not held back by poor FP64 performance. 
For gaming GPUs, mixed precision is a very good option if some loss of accuracy is acceptable.
FMM represents a middle ground, which at certain settings achieves 0 additional error increase over NGPB's default error level, while being significantly faster on gaming GPUs than the naive kernels.

\subsection{Naive Kernels}
\label{sec:implementation-energy-calculation-naive-kernels}

The first implementation was to create native kernels for all three energies: the Coulomb, polarization and ionic.
The result of the polarization energy is reused for the second term of the ionic energy Eq.~\ref{eq:ionic-energy}, as both a point-discrete.
This mirrors the original implementation.
The ionic kernel only calculates the first term of the ionic energy, or to be more specific, the triangle-discrete term Eq.~\ref{eq:ionic-energy-discrete}.
The atoms, charges, flux, triangle corners and normals where put into flat arrays and passed to the kernels as needed.
Even systems like 6VYB with 44k or 1VSZ 180k atoms fit comfortably into the 10GB of VRAM of an RTX 3080.

The Coulomb kernel is launched for all atoms in parallel.
Due to the triangular shape of the total sum, the workload across threads is wildly unbalanced.
However this turned out to be a very small issue, as the ionic and polarization kernels both take up more than 1000x of the time.

The polarization and ionic kernels are launched for all surface points and triangles in parallel.
It immediately became apparent, that those are the more computationally intense kernels, being highly FP64 bound.

Despite the fact that the optimization is very straight forward, the new GPU accelerated version of \texttt{energy\_\allowbreak{}fast}, dubbed \texttt{energy\_\allowbreak{}cuda\_\allowbreak{}fast} ran 6VYB 17x faster on the RTX 3080 and a whopping 240x faster on an A100.

\subsubsection{Further optimizations}

On the GPU side:
I used CUDA's \texttt{\_\allowbreak{}\_\allowbreak{}restrict\_\allowbreak{}\_\allowbreak{}} keyword of the data pointers, which prevents aliasing and enables more aggressive optimization by the compiler.
This something the compiler should handle automatically, but this keyword gives assurance and does nothing in the worst case.

Tiling was deemed ineffective.
Though it would have helped a bit for the Coulomb kernel, the gain was just 10x on a kernel that took around 1ms on 6VYB.
The other two kernels where heavily FP64 bound
and since tiling only helps with memory throughput it subsequently dropped.

A much more significant optimization was the use of the built-in inverse square root function \texttt{rsqrt}, instead of ``manually'' calculating the distance between bodies and diving by it.
This dropped the total time by another 25\%.
\newline
\newline
On the CPU side: 
Since the the polarization and ionic kernels both need the same charge and atom arrays as the Coulomb kernel, I've reused their device pointers, but the speedup of that was miniscule.

Lastly, I identified that the original code was computing \texttt{normal\_\allowbreak{}intersections} multiple times per quadrant edge.
Since the surfaces of marching cubes and NanoShaper should be nigh identical, the quadrant's edges for which the \texttt{normal\_\allowbreak{}intersections} are computed should be always be the edges of those quadrants, which are located at the surface $\Gamma$, so I precomputed them.

It is at this point that noticed that marching cubes and NanoShaper do unfortunately sometimes disagree, leading to \texttt{normal\_\allowbreak{}intersections} to return a default value without writing to the passed normal pointer at all.
Worse yet, this stale normal point then gets used in the calculation of the ionic energy.
After conversing with one of the authors of NGPB, we decided that the best course of action is to drop a surface triangle if one of its normals could not be determined.
For this I modified \texttt{normal\_intersection} to return \texttt{true} if it had found an intersection and \texttt{false} otherwise.
As this occurrence is very rare, it did not affect the speed, and even the accuracy in many cases.

\subsection{FMM}
\label{sec:implementation-energy-calculation-fmm}

Particularly for the polarization and ionic energies, it was obvious that in order to achieve any significant level of speedup, a more sophisticated approach was be required while retaining the level of accuracy.
For this purpose I implemented a fairly non-standard implementation of FMM, with the only ``normal'' things about it being the overall algorithm.
It uses a LBVH trees, iterative dual tree traverse with double sided $B_{max}$ MAC, spherical harmonic expansions with both associated-Legendre and pole-free Cartesian recurrence.

\subsubsection{Overview}
% TODO add overview
The rough structure of my implementation is as follows:
On the CPU side, the previously mentioned data packing takes place, as is the case with the naive kernels.
Then a LBVH source tree is constructed from the molecular particles.
Directly after its construction, the multipole expansions are passed upwards.
The source tree is reused for both energy calculations, while two different target tree are constructed for point-discrete and triangle-discrete calculations.
Then for each target tree, it traverses the source and target using DTT, and creates interaction lists for the far field and near field.
For the far field interactions, the M2L translations are performed and passed downwards using L2L.
Finally, both the L2P and P2P interactions are handled in a fused evaluation.

Figure~\ref{fig:fmm-overview} shows the same pipeline as a flow chart, split into the eight groups the sections below follow, and marks for each stage whether it runs on the host or on the device.
Each group is then broken out at the level of individual kernels in its own subsubsection, where the figure also records how every device kernel maps its work onto blocks and threads.

\subsubsection{Multipole Expansion}

Since both polarization energy Eq.~\ref{eq:polarization-energy} and the second term of the ionic energy Eq.~\ref{eq:ionic-energy} are variations of the Laplace kernel, I used spherical harmonics and the translation operators taken from ``A Fast Adaptive Multipole Algorithm in Three Dimensions'' paper \cite{cheng1999fastadaptive}. 
The first term though has a different shape $r/|r|^3$, which is equal to the gradient of the Laplace kernel $\nabla 1/|r| = r/|r|^3$.
To compute it, I used forward-mode automatic differentiation, through operator overloading.
The spherical harmonics of degree n and order m are computed with:
\begin{equation}
    Y_n^m(\theta, \phi) = \sqrt{\frac{(n-|m|)!}{(n+|m|)!}} \cdot P_n^{|m|}(\cos\theta) e^{im\phi}
    \label{eq:spherical-harmonics}
\end{equation}
where $P_n^{m}$ are the associated Legendre functions, which are given by:
\begin{equation}
    P_n^m(x) = (-1)^m (1-x^2)^{m/2} \frac{d^m}{dx^m} P_n(x),
    \label{eq:associated-legendre}
\end{equation}
with the $P_n(x)$ being Legendre polynomials computed by Rodrigues formula:
\begin{equation}
    P_n(x) = \frac{1}{2^n n!} \frac{d^n}{dx^n} (x^2-1)^n.
    \label{eq:legendre-rodrigues}
\end{equation}
I created a device function \texttt{solid\_harmonics}, which computes either the regular harmonics $Y_n^m(\theta,\varphi) \cdot r^n$ or the irregular harmonics $\frac{Y_n^m(\theta,\varphi)}{r^{n+1}}$.
I used spherical parametrization to calculate the necessary trigonometric functions from the Cartesian shift vector, avoiding the conversion from Cartesian to spherical coordinates.

Computing the derivative exposed one large problem: the derivative diverged at the gradient center, causing catastrophic accuracy loss for the ionic energy term.
Among other places, the regular harmonics appear in the L2P operator \ref{eq:l2l-potential}, where the the local expansion is evaluated at the leaf's center.
This is fine in the case of the potential, but diverges for derivative, so I evaluated regular harmonics using pole-free Cartesian recurrences derived from the recurrence relations in \cite{perezjorda1996solidharmonics} instead of the associated Legendre:
\begin{equation}
    diagonal: R_m^m = -\sqrt{\frac{2m-1}{2m}} (x+iy) R_{m-1}^{m-1},   R_0^0 = 1
\end{equation}
\begin{equation}
    vertical: R_n^m = \frac{2n-1}{\sqrt{(n-m)(n+m)}} \cdot z \cdot R_{n-1}^m - \sqrt{\frac{(n+m-1)(n-m-1)}{(n+m)(n-m)}} \cdot r^2 \cdot R_{n-2}^m
\end{equation}

The concrete forms of the translation operators used, following the notation of the paper, all rely on the coefficients:
\begin{equation}
    A_n^m = \frac{(-1)^n}{\sqrt{(n-m)!(n+m)!}}
    \label{eq:translation-coeff-a}
\end{equation}
%A source charge $q_l$ sits at spherical coordinates $(\rho_l, \alpha_l, \beta_l)$, while the evaluation point $X$ is at $(r,\theta,\phi)$, both relative to the expansion's center.
% The P2M formula, which forms a box's multipole coefficients $O_n^m$ directly from its charges, is the mirror image of the local-expansion formula below with the roles of source and target reversed, so it is omitted here.

\subsubsection{Local Expansion (L2P)}
A local expansion is the far field's counterpart valid inside a sphere around a point, generated by charges lying entirely outside it.
For $N$ charges $q_l$ it is
\begin{equation}
    \Phi(X) = \sum_{j=0}^{\infty}\sum_{k=-j}^{j} L_j^k \, Y_j^k(\theta,\phi) \, r^j
    \label{eq:local-expansion-potential}
\end{equation}
with coefficients
\begin{equation}
    L_j^k = \sum_{l=1}^{N} q_l \, \frac{Y_j^{-k}(\alpha_l,\beta_l)}{\rho_l^{j+1}}
    \label{eq:local-expansion-coeffs}
\end{equation}

\subsubsection{M2M}
M2M translates a multipole expansion with coefficients $O_n^m$, centered at $X_0=(\rho,\alpha,\beta)$, into an equivalent expansion $M_j^k$ centered at the origin, letting a parent node's expansion be assembled from its children's without ever revisiting the original charges:
\begin{equation}
    \Phi(X) = \sum_{j=0}^{\infty}\sum_{k=-j}^{j} \frac{M_j^k}{r^{j+1}} \, Y_j^k(\theta,\phi)
    \label{eq:m2m-potential}
\end{equation}
\begin{equation}
    M_j^k = \sum_{n=0}^{j}\sum_{m=-n}^{n} \frac{O_{j-n}^{k-m} \, i^{|k|-|m|-|k-m|} \, A_n^m \, A_{j-n}^{k-m} \, \rho^n \, Y_n^{-m}(\alpha,\beta)}{A_j^k}
    \label{eq:m2m-coeffs}
\end{equation}

\subsubsection{M2L}
M2L converts a multipole expansion $O_n^m$, centered at $X_0=(\rho,\alpha,\beta)$, into a local expansion $L_j^k$ valid inside a well-separated box, the single operator that turns particle-cluster interactions into cluster-cluster interactions and gives FMM its linear complexity:
\begin{equation}
    \Phi(X) = \sum_{j=0}^{\infty}\sum_{k=-j}^{j} L_j^k \, Y_j^k(\theta,\phi) \, r^j
    \label{eq:m2l-potential}
\end{equation}
\begin{equation}
    L_j^k = \sum_{n=0}^{\infty}\sum_{m=-n}^{n} \frac{O_n^m \, i^{|k-m|-|k|-|m|} \, A_n^m \, A_j^k \, Y_{j+n}^{m-k}(\alpha,\beta)}{(-1)^n \, A_{j+n}^{m-k} \, \rho^{j+n+1}}
    \label{eq:m2l-coeffs}
\end{equation}

\subsubsection{L2L}
L2L shifts a local expansion $O_n^m$, centered at $X_0=(\rho,\alpha,\beta)$, down to a local expansion $L_j^k$ centered at a child box, propagating the accumulated far-field contribution down the tree:
\begin{equation}
    \Phi(X) = \sum_{j=0}^{p}\sum_{k=-j}^{j} L_j^k \, Y_j^k(\theta,\phi) \, r^j
    \label{eq:l2l-potential}
\end{equation}
\begin{equation}
    L_j^k = \sum_{n=j}^{p}\sum_{m=-n}^{n} \frac{O_n^m \, i^{|m|-|m-k|-|k|} \, A_{n-j}^{m-k} \, A_j^k \, Y_{n-j}^{m-k}(\alpha,\beta) \, \rho^{n-j}}{(-1)^{n+j} \, A_n^m}
    \label{eq:l2l-coeffs}
\end{equation}
The coefficient order grows outward with the degree $n$ by $2n+1$, meaning that an expansion of degree 1 $M_1^m$ has 3 coefficient, while $M_2^m$ has 5, $M_3^m$ has 7 etc.
A coefficient $M_n^m$ is always the complex conjugate of $M_n^{-m}$. 
This allowed me to pack them in a lower-triangular layout, with interleaving real and imaginary parts, storing only the positive $m$.
To get the coefficient $M_n^{-m}$, I simply looked up $M_n^m$, and inverted its imaginary part.

\subsubsection{Tree Construction}

Both the source and the target tree are constructed using Karras's LBVH algorithm\cite{karras2012lbvh}, whose prerequisite is a bounding box over all bodies.
I compute this one the GPU by finding the minimum and maximum coordinates in all the spacial dimensions with the \texttt{bbox\_kernel}.
In combines custom atomicMinDouble and atomicMaxDouble into 6 shared variables per block, before comparing the result of the block against the global memory.
Although not efficient, this at least reduces the traffic from once per thread to 6 times the amount of blocks.
Running 1VYZ and 6VYB, this kernel only took only tens of microseconds.

The resulting structure is a binary radix tree, which is different from a traditional octree used in FMM.
However, it is practically the same spacial decomposition.
To get an ``octant'' of a node, one must simply descend it three levels, though this does mean that my tree depth is essentially 3x that of an equivalent octree.
I have to point out though that those ``octants'' aren't actually that, because LBVH creates tight boxes around a cluster of particles, rather than bisected quadrants.
This has both upsides and downsides.
On one side I need to traverse 3x as many times as I would with a octree.
On the other I achieve greater MAC granularity, since I only split nodes two, instead of 8.

Each leaf of the LBVH only contains a single atom.
However, this is overly granular and wasteful.
In order to cluster them into leafs with a certain number of atoms, I classified them into nodes on whether they cover enough atoms.
Logically, a parent node whose child covers enough nodes automatically does so as well.
These nodes are called the box nodes, and they are the only ones that will be carrying the coefficients and moments of the multipole expansions.
This not only eases calculation, it also drastically reduces memory consumption, as the non-box nodes far outnumber them.

For the clustered leaf size, I settled on 256 through experimentation.

\subsubsection{Traversal}

%It's not actually traversal, I just collect the interaction lists
The traverse is a breadth-first-descend based on DTT \cite{yokota2013dualtree} algorithm described in \ref{sec:alternative-techniques-nbody-fmm-dtt}, using the double sided $B_{max}$ MAC controlled through $\theta$.
Rather than the $B_{\max}$ of each cell, I use the half-diagonals $r_A$ and $r_B$ of the bounding boxes, accepting a pair when $r_A + r_B < \theta R$
(Figure~\ref{fig:fmm-mac}).
\input{figures/mac_criterion}
Instead of evaluating the interactions during the traverse itself, I construct a list of near field (P2P) and far field (M2L) interaction, essentially doing what traditional FMM does, although using a MAC.
My version is also recursive, but iterative, which processes the entire frontier in a level-synchronous loop.
Each iteration calls the \texttt{fmm\_pair\_kernel}, which does the same classifications, as the regular DTT, but emits the M2L, P2P and next frontier pairs.
An important distinction is also that a ``leaf'' is considered the smallest box node, not the smallest node in the tree.
Since the buffer size can not be dynamically changed, I started the traversal with an estimate.
The buffer cap starts out at $2^18$ and climbs a power-of-two ladder until it is either larger than 1 GiB, or $64 \cdot n_{box}$.
If the buffers overflowed it would increase the buffer size by 4 and try again.
% For the double sided MAC, the M2L interaction list for a cell forms a constant-thickness shell on a sphere with a radius of roughly $1/\theta$ meaning it list size grows with \(\mathcal{O}(\theta^{-2})\) \cite{yokota2012hierarchical}.
% The P2P list then takes up the inner volume the sphere, which grows with \(\mathcal{O}(\theta^{-3})\).
% pretty much BS because I don't have an octree
Through some experimentation, I found that the number of P2P interactions per box node only exceeded 64, when $\theta$ was set to 0.1 --- a uselessly small number which slows the algorithm down to a crawl.
Even in that case the ladder would overstep $64 \cdot n_{box}$ once more, since only the next power of two would be greater.
This approach is surprisingly robust, and has not lead to overflows, even when calculating the energies for really large systems like H1N1.
