\section{BIMPP}
\label{sec:implementation-bimpp}

Though it is just a dependency of NGPB, some systems of BIMPP were in dire need of optimization.
These optimizations ended up being CPU only.
I created a private fork of it, which I used instead of the special NGPB release.

\subsection{sparse\_matrix\_template}
\label{sec:implementation-bimpp-sparse-matrix-template}

BIMPP stores both local and non-local values of the distributed sparse matrix in a \texttt{std::vector} of \texttt{std::map<int, double>}.
In \texttt{x86\_64} \texttt{libstdc++}, \texttt{std::map} is implemented using a red-black tree, whose node is comprised of 3 pointers, a color enum, and a \texttt{std::pair}.
The three pointers exist for the parent, left and right at take up 24 Bytes.
The color enum, including padding takes up 8 Bytes.
In the context of the distributed sparse matrix, the \texttt{std::pair} is a tuple of type \texttt{<int const, double>}.
So 4 Bytes for the integer, plus 4 Bytes for padding and 8 Bytes for the double comes out to 16 Bytes.
All together this totals 48 Bytes.

In comes \texttt{flat\_map} from the already reference \texttt{boost} library.
It is a vector based implementation rather than a tree based one.
Its memory footprint is just 24 B, essentially half.
This change is also minimally invasive, only changing an underlying data type in the \texttt{sparse\_matrix\_template} of BIMPP.

This does not solve the issue of the global row being replicated on each rank.
For this a more sophisticated communication patter needs to be used, as was demonstrated in the SHIRO paper \cite{zhuang2025shiro}.

\subsection{bim3a\_solution\_with\_ghosts}
\label{sec:implementation-bimpp-bim3a-solution-with-ghosts}

As explained before in \ref{sec:nextgenpb-libraries-bimpp-bim3a-solution-with-ghosts}, this function is used throughout NGPB because it handles the exchange of non-local- and ghost values through a lot of expensive calculations.
First it updates every quadrant and its neighbors with \texttt{quadrant\_t::update()} hidden inside \texttt{quadrant\_iterator::operator++()}, without skipping those that have been already updated as the neighbor.
This also computes the physical vertex positions through \texttt{p8est\_qcoord\_to\_vertex}, which go completely unused.

Turns out, this is not necessary at all. 
\texttt{p4est} already stores this information.
All I did is reuse it.
To get all the non-owned nodes reference by the local ones, I referenced \texttt{lnodes->nonlocal\_nodes}.
For the ghost layer quadrants, I iterated through \texttt{tmesh\_3d::ghost\_data}, which is always 40 entries long per ghost.
This drastically reduces the runtime at multiple points in the code.

\section{Energy Calculation}
\label{sec:implementation-energy-calculation}

Since ray cache is relatively hard to port to the GPU, I decided to go for a simpler route:
Keep the classification, flux and normal calculation on the CPU.
They are essentially just lookups on the ray cache, which take very little time.
Reformulating them was not worth it. 
Besides, the true weight of the computational effort lies in the pairwise interactions themselves.
Thus the idea was to collect the necessary data into flat arrays, to then do execute those on the GPU.
At the end, I settled on 3 implementations, each being a viable option in different scenarios.
The naive implementation or kernels are surprisingly useful on workstation GPUs, which are not held back by poor FP64 performance. 
For gaming GPUs, mixed precision is a very good option if some loss of accuracy is acceptable.
FMM represents a middle ground, which at certain settings achieves 0 additional error increase over NGPB's default error level, while being significantly faster on gaming GPUs than the naive kernels.

\subsection{Naive Kernels}
\label{sec:implementation-energy-calculation-naive-kernels}

The first implementation was to create native kernels for all three energies: the Coulomb, polarization and ionic.
The atoms, charges, flux, triangle corners and normals where put into flat arrays and passed to the kernels as needed.
Even systems like 6VYB with 44k or 1VSZ 180k atoms fit comfortably into the 10GB of VRAM of an RTX 3080.

The Coulomb kernel is launched for all atoms in parallel.
Due to the triangular shape of the total sum, the workload across threads is wildly unbalanced.
However this turned out to be a very small issue, as the ionic and polarization kernels both take up more than 1000x of the time.

The polarization and ionic kernels are launched for all surface points and triangles in parallel.
It immediately became apparent, that those are the more computationally intense kernels, being highly FP64 bound.

Despite the fact that the optimization is very straight forward, the new GPU accelerated version of \texttt{energy\_\allowbreak{}fast}, dubbed \texttt{energy\_\allowbreak{}cuda\_\allowbreak{}fast} ran 6VYB 17x faster on the RTX 3080 and a whopping 240x faster on an A100.

\subsubsection{Further optimizations}

On the GPU side:
I used CUDA's \texttt{\_\allowbreak{}\_\allowbreak{}restrict\_\allowbreak{}\_\allowbreak{}} keyword of the data pointers, which prevents aliasing and enables more aggressive optimization by the compiler.
This something the compiler should handle automatically, but this keyword gives assurance and does nothing in the worst case.

Tiling was deemed ineffective.
Though it would have helped a bit for the Coulomb kernel, the gain was just 10x on a kernel that took around 1ms on 6VYB.
The other two kernels where heavily FP64 bound
and since tiling only helps with memory throughput it subsequently dropped.

A much more significant optimization was the use of the built-in inverse square root function \texttt{rsqrt}, instead of ``manually'' calculating the distance between bodies and diving by it.
This dropped the total time by another 25\%.
\newline
\newline
On the CPU side: 
Since the the polarization and ionic kernels both need the same charge and atom arrays as the Coulomb kernel, I've reused their device pointers, but the speedup of that was miniscule.

Lastly, I identified that the original code was computing \texttt{normal\_\allowbreak{}intersections} multiple times per quadrant edge.
Since the surfaces of marching cubes and NanoShaper should be nigh identical, the quadrant's edges for which the \texttt{normal\_\allowbreak{}intersections} are computed should be always be the edges of those quadrants, which are located at the surface $\Gamma$, so I precomputed them.

It is at this point that noticed that marching cubes and NanoShaper do unfortunately sometimes disagree, leading to \texttt{normal\_\allowbreak{}intersections} to return a default value without writing to the passed normal pointer at all.
Worse yet, this stale normal point then gets used in the calculation of the ionic energy.
After conversing with one of the authors of NGPB, we decided that the best course of action is to drop a surface triangle if one of its normals could not be determined.
For this I modified \texttt{normal\_intersection} to return \texttt{true} if it had found an intersection and \texttt{false} otherwise.
As this occurrence is very rare, it did not affect the speed, and even the accuracy in many cases.

\subsection{FMM}
\label{sec:implementation-energy-calculation-fmm}

It was obvious that in order to retain the level of accuracy a more sophisticated approach was be required to achieve any significant level of speedup.
For this purpose I implemented a fairly non-standard implementation of FMM, with the only ``normal'' things about it being the overall algorithm.
It uses a LBVH trees, iterative dual tree traverse with double sided $B_{max}$ MAC, spherical harmonic expansions with both associated-Legendre and pole-free Cartesian recurrence.

Both the source and the target tree are constructed using Karras's LBVH algorithm\cite{karras2012lbvh}, whose prerequisite is a bounding box over all bodies.
I compute this one the GPU by finding the minimum and maximum coordinates in all the spacial dimensions with the \texttt{bbox\_kernel}.
In combines custom atomicMinDouble and atomicMaxDouble into 6 shared variables per block, before comparing the result of the block against the global memory.
Although not efficient, this at least reduces the traffic from once per thread to 6 times the amount of blocks.
Running 1VYZ and 6VYB, this kernel only took only tens of microseconds.

The resulting structure is a binary radix trees, which is different from a traditional octree used in FMM.
However, it is practically the same spacial decomposition.
To get an ``octant'' of a node, one must simply descend it three levels, though this does mean that my tree depth is essentially 3x that of an equivalent octree.
I have to point out though that those ``octants'' aren't actually that, because LBVH creates tight boxes around a cluster of particles, rather than bisected quadrants.
This has both upsides and downsides.
On one side I need to traverse 3x as many times as I would with a octree.
On the other I achieve greater MAC granularity, since I only split nodes two, instead of 8.

I used spherical harmonics and the translation operators, such as the translation operators are taken from ``A Fast Adaptive Multipole Algorithm in Three Dimensions'' paper \cite{cheng1999fastadaptive}, which I used for the calculation of the polarization Eq.~\ref{eq:polarization-energy} and the second term of the ionic energy Eq.~\ref{eq:ionic-energy}.
The first term though has a different shape $r/|r|^3$.
Luckily, this is not a problem because is this simply the derivative of the Laplace kernel $\nabla 1/|r| = r/|r|^3$.
