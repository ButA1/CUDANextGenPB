\chapter{NextGenPB}
\label{sec:nextgenpb}

At the time of writing, Next Generation Poisson-Boltzmann (NextGenPB or NGPB for short) \cite{diflorio2025nextgenpb} is the most recent innovation in the field of LPBE solvers, aiming to improve accuracy while maximizing computational efficiency. 
It is purposefully modular and built upon free and open libraries, making improvements to individual steps easier, though, as I will explain later, this has to be taken with a grain of salt.
It is part of the family of grid- or FEM-based solvers, featuring local (de)refinement using the p4est library.
% TODO I don't like this explanation of how it uses libraries at all
Using MPI and MPI-aware mathematical libraries like BIMPP and LIS to handle calculations across distributed nodes, it lends itself well for high performance computing.
Its main attractions are the use of NanoShaper and an enhanced analytical approach, allowing for much more accurate energy calculation, beating out many older LPBE solvers in both accuracy and speed --- an impressive feat that has gained the attention of biomolecular chemists at our technical university, who seek to replace their T-ABPS with NGPB.
% yes I actually put that em dash there

To avoid the self-energy singularity, NGPB computes the electrostatic energies individually, where each of them is never evaluated at the atom's center.
This is an entirely new approach, which avoids reformulating, doing additional differencing or using a different model other than point charges.
Thus the total electrostatic energy NGPB computes is a sum of the Coulomb, polarization and ionic energy.

\section{Libraries}
\label{sec:nextgenpb-libraries}

\subsection{NanoShaper}
\label{sec:nextgenpb-libraries-nanoshaper}

NanoShaper \cite{abate2025nanoshaperweb} is a surface reconstruction and pocket detection tool aimed at biomolecular systems.
It is compatible with patch-based, implicit surfaces or triangulated surfaces and works by casting rays in a grid pattern, computing both surface intersections and normals. 
The authors of NGPB leverage this by aligning the grid of their problem space with that of NanoShaper, giving them the necessary surface information essentially for free.

\subsection{P4est}
\label{sec:nextgenpb-libraries-p4est}

P4est \cite{carsten_burstedde_2024_10839051} is a library for dynamic management of adaptive quadtrees, while octrees are taken care of by its submodule p8est.
It is designed for parallel work and scales well on many-core systems, though unfortunately, it has not been officially adapted to work on GPUs.
NGPB uses it for creating and adapting octrees by refining, coarsening, and enforcing 2:1 conditions between neighbors. It also uses it to partition the octree between MPI processes and handle the communication between them.

\subsection{BIMPP}
\label{sec:nextgenpb-libraries-bimpp}

BIMPP \cite{defalco_bimpp} is a very obscure library written by one of the co-authors of NGPB. 
NGPB does not use the standard version of it, but rather a special ``NextGenPB-v0.0.01'' release, which contains additional operators meant specifically for NGPB.
Due to the lack of documentation, it is difficult to get an overview over all its features.
I would describe it as library that enables distributed vector- and sparse matrix operations on quad- and octrees.
It itself is based on p4est, and it too handles the communication of non-local elements between the MPI processes.

In order to perform parallel computations on a sparse matrix, they are broken up into segments, where each node (or process) handles one of them locally.
However, this creates an issue where some operations would affect non-local entries of segments that belong to another node.
Those non-local changes need to be communicated after each operation.
The current implementation is known to be memory inefficient. 
The main culprit is the way BIMPP stores its distributed sparse matrix. 
For every rank, BIMPP holds both local and non-local values of a distributed sparse matrix in a \texttt{std::vector} of \texttt{std::map}, where the \texttt{std::vector} is sized to the global amount of rows.
\texttt{std::vector} initializes an empty map for every entry.
This means that matrix rows, that don't even need to track any non-locals still initialize an empty \texttt{std::map}.
This is particularly painful the global amount is very large, while also launching a lot of MPI ranks, as the total memory usage increases, which each additional rank.

\subsubsection{bim3a\_laplacian\_frac}
\label{sec:nextgenpb-libraries-bimpp-bim3a-laplacian-frac}

This is one of the proprietary functions only found in the NGPB-specific release I mentioned, and a critical step in the numeric solution.
Its purpose is to build the laplacian matrix operator by mapping a function to compute the intersection point $\alpha$, to then evaluate the effective electric permittivity $\varepsilon_{eff}$ using the weighted harmonic average (WHA) of the permittivity of the solute and the molecule $\varepsilon_{1}$ and $\varepsilon_{2}$.

\begin{equation}
    \varepsilon^{eff} = \frac{1}{\dfrac{\alpha}{\varepsilon_1} + \dfrac{(1-\alpha)}{\varepsilon_2}}
    \label{eq:effective-permittivity}
\end{equation}

\subsubsection{bim3a\_solution\_with\_ghosts}
\label{sec:nextgenpb-libraries-bimpp-bim3a-solution-with-ghosts}

This is the function that handles the communication of non-locals of distributed vectors computed from the octree mesh, between the ranks and is used many times throughout NGPB, like for example \texttt{create\_markers}, \texttt{create\_density\_map}.

During my work on the thesis, it became increasingly obvious that this function took way longer than it should.
This function rediscovers non-local and ghost quadrants of the octree, that each rank can see, running costly updates quadrants multiple times.

It then finally calls \texttt{remap()}, which collects all the non-local values from the other ranks, and \texttt{assemble()} which distributes the updated values.

\subsection{LIS}
\label{sec:nextgenpb-libraries-lis}

The library of Iterative Solvers for linear systems \cite{lis_library} is an MPI- and OpenMP-aware (and therefore parallel) software library for solving linear equations and Eigenvalue problems using iterative methods.
It supports both dense matrices, as well as CSR matrices.
As is typical for a linear software library, it offers many different solver methods and preconditioners.

\subsection{mumps}
\label{sec:nextgenpb-libraries-mump}

The multifrontal massively parallel sparse direct solver \cite{mumps_solver} is an alternative solver available in NGPB.
Unlike LIS this is a dense solver.
It not only accepts dense and CSR matrices, it can also accepts dictionary formats.
It uses LU factorization to simplify the matrix.

\section{Submodules}
\label{sec:nextgenpb-submodules}

The flow of NGPB can be roughly summarized by the following stages:
\begin{itemize}
    \item Reading inputs
    \item Grid \& Surface construction
    \item Matrix assembly
    \item Solving Linear Equation
    \item Energy calculation
\end{itemize}

\subsection{Input}
\label{sec:nextgenpb-submodules-input}

NGPB reads in settings and parameters via PRM files, which are given as an argument to the \texttt{ngpb} command.
These settings include the path to the molecule, mesh settings, simulation parameters and algorithmic settings.

\subsubsection{Mesh Settings}

NGPB offers four different mesh types, on which the remaining mesh parameters depend \cite{nextgenpb_docs}. 
The first and default option is \snakecase{mesh_shape = 0}, which is a de-refined mesh with a fine and coarse region.
The parameters \texttt{perfil1} and \texttt{perfil2} (short for ``percentage fill'') set the fraction of the fine and coarse domain size occupied by the molecule, so the higher the value, the tighter the corresponding region wraps around it. 
Their default values are 0.8 and 0.2 respectively.

Logically, one would want the molecule to be fully inside the fine grid domain but also leave enough room for the Stern Layer. This is a thin layer only a few Ångström thick, that exists on the surface of solids submerged in a solution, in which charged particles behave differently.
The inclusion of the Stern Layer is optional, and controlled through the \snakecase{stern_layer_surf} parameter and its thickness with \snakecase{stern_layer_thickness}.

Resolution with this mesh type is controlled through \texttt{scale}. Its value is equal to the inverse resolution in Ångström, meaning that a value of 2 corresponds to a resolution of 0.5 \,\AA{}. This resolution only applies to the fine region.

Lastly, there was also the undocumented parameter \snakecase{loc_refinement}, which could basically force the mesh to be refined regardless of \snakecase{mesh_shape}, and thus route the energy calculation through the \texttt{energy} function instead of \snakecase{energy_fast}.

\subsubsection{Simulation Parameters}

In this section, users can set the physical properties of the system. 
First an foremost are the dielectric constants of the molecule and the solvent relative to vacuum permittivity $\varepsilon_0$.
Then come the solvent properties like ionic strength and temperature.
It also offers different boundary conditions, which tell how the system how the electrostatic potential has to behave at the edge of the system.
Lastly, it controls which energies get computed. For my purposes I enabled \snakecase{calc_coulombic} and set \snakecase{calc_energy} to 2, meaning it computes all 3 energies.

\subsubsection{Algorithmic Parameters}

Here the user may choose between LIS and mumps, and in the case of the former, also allows for more detailed options.
By default it selects LIS with the following settings:
\begin{itemize}
    \item linear solver: CGS
    \item preconditioner: SSOR (Symmetric successive over-relaxation)
    \item accuracy: 1.e-6
\end{itemize}
Oddly enough, mumps is only mentioned in the references of the NGPB paper, while LIS is mentioned at least once.

\subsubsection{PDB and mmCIF files}

PDB is a legacy file format used by the protein data bank, a data base that catalogues proteins, which gives them their characteristic ID.
They only contain the atomic coordinates, as well as residue and chain information.
They're missing the partial charges and atomic radii, and require additional SIZ and CRG files for radii and charges to work inside NGPB.
Alternatively, they can be converted to PQR using \texttt{pdb2pqr} from the APBS toolset.

PDB have a 5 digit limit for the number of atoms, meaning the largest model it could represent would be 99 999 atoms big.
To solve this limitation, a new file mmCIF or PDBx type was introduced.
As of now, \texttt{pdb2pqr} is not capable of converting this new file type correctly. 
Researchers work around this by converting to mmCIF to PDB first, which means that for structures larger than 99 999 atoms like 1vsz all indices after that lose their last digit.
Fortunately NGPB does not care about these indices and simply gives them their own as it goes through the file line by line.

\subsection{Grid \& Surface Construction}
\label{sec:nextgenpb-submodules-grid-surface-construction}

As mentioned in \ref{sec:nextgenpb-submodules-input}, I will focus solely on the derefined mesh (\snakecase{mesh_shape = 0}).
NGPB uses p8est to construct the octree, where the fine region is nested inside the corse region.
It places the molecule inside the fine region so that \texttt{perfil1}
is satisfied for every dimension.
In a sense this fine region retains the aspect ratio of the molecule.
The coarse region on the other hand cannot always satisfy \texttt{perfil2} exactly, because the octree can only bisect.
The finest cell size has to be $1/scale$.
An octree can only bisect, so at level-L the size equals to $2^L/scale$.
This is why the size gets doubled until $l_{max}/size < perfil2$ is satisfied, where $l_{max}$ is the longest side of the molecule.
This also means that the coarse region is always cubic.
P4est maintains a 2:1 level ratio between the fine region and the coarse region, resulting in a transition region, which is always situated outside the fine region.
This is standard practice with octrees an avoids quadrants that share no vertices with their immediate neighbors.

\subsubsection{Ray Cache}

This is central component that gets used throughout multiple stages.
As its name suggests it holds the information about the rays cast by NanoShaper.
It stores a list of intersections and normals as an object \snakecase{crossing_t} under coordinates on an axis plane. 
The first index for the outmost array is the axis, so in a 3D environment those are the axes x,y and z. 
The next two for the binary tree map are the coordinates on the perpendicular plane along said axis.
The intersections are then the coordinates along the axis, which together with the coordinates on the plane gives you the point of each intersection.
Normals are triplets ordered by the intersection.
Lastly, \snakecase{crossing_t} also have an \texttt{init} flag, symbolizing whether the ray has to be recast.
This is a very efficient representation that is unfortunately not portable to the GPU, due to the binary tree map, whose values are complex structs, not simple types.

It is initialized in the method \snakecase{init_analytical_surf_ns}, where NanoShaper is used to cast rays in the fine region using the same $1/scale$ grid and finally stored in the cache.
This happens only on rank 0, leaving the ray cache of the other ranks initially empty.

Casting additional rays recast individually using \snakecase{compute_ns_inters} or in a batch using \snakecase{compute_pending_rays}.
The latter goes through the cached rays and uses the \texttt{init} flag of \snakecase{crossing_t} to determine, whether they should be recomputed.

The method \snakecase{fill_cache} then scatters rays from the rank 0 cache. The necessary rays are computed inside \snakecase{create_markers}. It too can call \snakecase{compute_ns_inters} implicitly if requested rays are missing from the cache or are uninitialized.

\subsubsection{create\_markers}

This function primarily classifies quadrants as either being inside, outside or on the border of the molecule.
Its secondary functions are redistribution of ray information to all ranks, and casting additional rays if needed.
For rank 0, it checks whether rays are present in the ray cache using \snakecase{is_in_ns_surf}, which adds casts a new ray on a miss.
Additional rays may also be cast for refined meshes, which have quadrants that are smaller than $1/scale$.
For the remaining ranks, it collects a list of rays that it needs.
Rank 0 then distributes those rays to the corresponding ranks using \snakecase{fill_cache}.

\subsection{Matrix Assembly}
\label{sec:nextgenpb-submodules-matrix-assembly}

This step produces the matrix operator and the right-hand-side (RHS) vector needed for the linear equation.

\subsubsection{create\_density\_map}

This method computes the RHS of the linear equation from the fixed charge densities.
It calls \snakecase{bim3a_solution_with_ghosts} twice.

\subsubsection{cube\_fraction\_intersection}

This method computes the fraction of each edge that is inside the molecule, by looking up intersection edge aligned rays from the ray cache.
It then takes the last intersection point it finds and computes its length relative to the staring edge vertex, which it then divides by the total edge length.

\subsubsection{assemble\_system\_matrix}

This method allocates the CSR matrix and computes the operator using \snakecase{bim3a_laplacian_frac} in combination with \snakecase{cube_fraction_intersection}.
It is by far the most memory intensive step, due to BIMPP architectural choices explained in \ref{sec:nextgenpb-libraries-bimpp}.
This step also applies the boundary condition.

\subsection{Solving the Linear Equation}
\label{sec:nextgenpb-submodules-solve-linear-equation}

In this step the linear PBE is solved for the electrostatic potential.
Depending on which solver is selected in the PRM file, this is either done with \snakecase{lis_compute_electric_potential} or \snakecase{mumps_compute_electric_potential}.
Relying heavily on matrix operations, this step is a great candidate for GPU acceleration.
Libraries like cuDSS and AMGX can be easily implemented here.

\subsection{Energy Calculation}
\label{sec:nextgenpb-submodules-energy-calculation}

This step finally computes the 3 energies, as well as the total energy of the system.
Depending on whether the mesh has been refined, NGPB chooses between two sets of methods.
Methods suffixed by ``fast'' assume that the mesh is unrefined, and as the name implies, skips certain steps that would be needed it were.
The main two methods here are \texttt{energy} and \snakecase{energy_fast}, which compute the energies according to the following formulas:

The Coulomb energy is the typical interaction between two charged particles $q_i$ and $q_j$ without self-interaction, so $\lVert \mathbf{r}_i - \mathbf{r}_j \rVert$ in Equation~\eqref{eq:Coulomb-energy} never equals 0. 
\begin{equation}
    E_{coul} = \sum_{i=1}^{N_{atoms}} \sum_{j<i} \frac{q_i q_j}{4\pi\varepsilon_m \lVert \mathbf{r}_i - \mathbf{r}_j \rVert}
    \label{eq:Coulomb-energy}
\end{equation}
This formulation already avoids unnecessary interactions, by essentially evaluating only the triangle of the matrix spanned by the $N \times N$ interaction.

The polarization energy arises from polarization charges at the surface where the dielectric constant jumps. It is always evaluated on the intersection point $r_p$ between the surface and the grid.
The authors approximate the electric flux along a surface patch with:
\begin{equation}
    D_v^{eff} = - \varepsilon^{eff}(\phi_2 - \phi_1)/h_v
    \label{eq:electric-flux}
\end{equation}
where $\varepsilon^{eff}$ is the WHA according to Eq.~\ref{eq:effective-permittivity}.
It uses \snakecase{classifyCube_flux(_fast)} to gather the necessary values per quadrant.
The total polarization charge is computed with:
\begin{equation}
    q_p \approx \varepsilon_0 \left( \frac{1}{\varepsilon_s} - \frac{1}{\varepsilon_m} \right) D_v^{eff} h_v^2
    \label{eq:polarization-charge}
\end{equation}
where $h_v^2$ is the area of the surface patch associated with the intersection point.
Summing the interaction of every such polarization charge with every atomic charge then gives the polarization energy:

\begin{equation}
    E_{pol} = \frac{1}{2} \sum_{i=1}^{N_{atoms}} \sum_{p=1}^{N_{Ic}} \frac{q_i q_p}{4\pi\varepsilon_0 \lVert \mathbf{r}_p - \mathbf{r}_i \rVert}
    \label{eq:polarization-energy}
\end{equation}

The ionic energy is generated by the interaction between the solvent counterions and the charges of the solute, and it is very small compared to the polarization and Coulomb energies.
Computing it would require doing an expensive volume integration over the entire solute volume, which is why it was either avoided, computed implicitly by evaluating the total energy directly, or computed indirectly through multiple runs with different ionic strengths.
However, using Green's identities, the authors of NGPB converted the volume integral into a surface integral over $\Gamma$.

\begin{equation}
    E_{ion} = \frac{1}{2} \sum_{i=1}^{N_{atoms}} q_i \left( \int_{\Gamma} \phi(\tilde{\mathbf{r}}) \frac{(\tilde{\mathbf{r}} - \mathbf{r}_i) \cdot \mathbf{n}(\tilde{\mathbf{r}})}{4\pi \lVert \tilde{\mathbf{r}} - \mathbf{r}_i \rVert^3} \, dS - \frac{1}{\varepsilon_s} \int_{\Gamma} \frac{\mathbf{D}(\tilde{\mathbf{r}}) \cdot \mathbf{n}(\tilde{\mathbf{r}})}{4\pi \lVert \tilde{\mathbf{r}} - \mathbf{r}_i \rVert} \, dS \right)
    \label{eq:ionic-energy}
\end{equation}

As stated in the NGPB paper, the second integral is the same, and instead of recomputing, the intermediate result from the polarization energy calculation gets reused.
The first integral, denoted $I$, is discretized using triangles instead of surface points.
To get these triangles NGPB uses \snakecase{classifyCube(_fast)}, which uses marching cubes to locally re-triangulate the surface.
Let $N_t$ be the totality of all triangles.
Then the first integral can be computed discretely as follows:

\begin{equation}
    I \approx \sum_{j=1}^{N_t} \frac{T_j}{3} \sum_{k=A,B,C} \phi(\mathbf{r}_k) \frac{(\mathbf{r}_k - \mathbf{r}_i) \cdot \mathbf{n}(\mathbf{r}_i)}{4\pi \lVert \mathbf{r}_k - \mathbf{r}_i \rVert^3}
    \label{eq:ionic-energy-discrete}
\end{equation}

where $T_j$ is the area of the $j$-th triangle and $A$, $B$ and $C$ are the three corner nodes.
The normal is taken from the ray cache using \texttt{normal\_intersection}, which turns out, is not always there.
In very rare cases, NanoShaper and marching cubes disagree on where the surface is exactly.
Marching cube can only find triangles, whose corners always lay in the middle of the quadrant's edges.
In theory, NanoShaper's rays are aligned with those edges and should thus find the intersections along them.
However, if marching cubes finds a triangle where NanoShaper has not found any intersections, it also will not have any normal vector for it.

The total energy is then simply the sum of all three contributions:

\begin{equation}
    E_{tot} = E_{coul} + E_{pol} + E_{ion}
    \label{eq:total-energy}
\end{equation}

\subsubsection{classifyCube(\_fast)}

This method computes the triangulation for a cube using the marching cube algorithm.
The value it returns is an 8-bit marching cube index.
It is exclusively used for the ionic energy calculation.
Because all fine region quadrants are at $1/scale$ when no refinement is done, the \texttt{fast} version skips checking for hanging nodes.

\subsubsection{classifyCube\_flux(\_fast)}

This method returns the $\varepsilon$ and $\phi$ for each quadrant's node.
Just like in \snakecase{classifyCube(_fast)}, the \texttt{fast} version also ignores hanging nodes.
Additionally it computes the flux direction along the edges, on which the $\varepsilon$ changes.

\subsubsection{normal\_intersection}

This method fetches the intersection point and normal on an edge, by looking for a ray in the ray cache, which is exactly aligned with it.
It then searches for intersections between the edge start node and the end node.
It is a impure function, writing both its answers to pointer supplied to it.
