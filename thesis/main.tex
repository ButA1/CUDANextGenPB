\subsection{Experimental Setup}
\label{sec:evaluation-experimental-setup}

In this section, I will describe the experimental setup used to evaluate the performance of the various optimizations and compare them against the baseline implementation and analytical results, but before that I want to go over the relevant parameters inside my experimental setup.

\subsubsection{NGPB Parameters}
\label{sec:evaluation-experimental-setup-ngpb-parameters}

One important parameter is \texttt{perfil}, which is short for "percentage fill". The documentation for NGPB \cite{example2010} 
% TODO add citation here
describes it as the "fraction of the fine/coarse domain size occupied by the molecule", where \texttt{perfil1} controls the fraction for the fine domain, and \texttt{perfil2} the coarse domain. They can be thought of as controlling two bounding boxes around the molecule. Logically, you want the molecule to be fully inside the fine grid domain. Perfil1 is set to 0.8 by default, however the in the NGPB paper \cite{diflorio2025nextgenpb}, the authors showed that a \texttt{perfil1} of 90\%-95\% is perfectly sufficient. This is something I also observed.

\subsubsection{Compiler Flags}
\label{sec:evaluation-experimental-setup-compiler-flags}

Aside from the additional compiler flags added due to inclusion of CUDA, I largely used the same flags from the original makefile and \texttt{local\_settings}. Although initially I changed the optimization flag from \texttt{-o2} to \texttt{-o0} due to fears of catastrophic cancellations during floating point calculations, it quickly proved more trouble than it was worth. It made the code extremely slow, which over-exaggerated the speedup achieved by the GPU and the need to optimize other parts of the code. I reverted back to \texttt{-o2}, but purposefully stayed away from the \texttt{-Ofast -mtune=native -march=native} lingering inside the \texttt{local\_settings}, which would've provided even faster baseline performance, but unlike \texttt{-o2} legitimately ran the risk of altering the results. Additionally, the dependencies of NGPB as also compiled using \texttt{-o2}.

\subsubsection{Testing}
\label{sec:evaluation-experimental-setup-testing}

The main two metrics used for evaluation were the execution time, accuracy of the results and also in some instances, memory usage. For this I created a handful of test cases using mostly different PQR files. Those generally fall into two categories: analytical test cases and comparative test cases. 

The analytical test cases were used to verify the correctness of the results with respect to the known analytical results taken from the NGPB paper \cite{diflorio2025nextgenpb}. Those allowed me to verify the error magnitudes independent of actually running NGPB locally, as well as the correctness of the parameters used to achieve the results from the paper. They were not used to compare speed, as they are fairly small and thus not very computationally expensive.

Comparative test cases were used to compare the results of the optimized implementation against the baseline. The baseline isn't formed by the completely unmodified version of NGPB, as the slightly altered result due to the triangulation fix is assumed to be more correct. Unlike the analytical benchmarks, these were used to compare both speed and accuracy, as they are much larger than the analytical models. 

The version of the dependencies had to be kept the static. Using NanoShaper Version 0.8 instead of the official 1.5 altered the result. Similarly, I needed switch to the unmodified version of BIMPP, sine it was partially optimized as part of this thesis in a private fork. The versions of the remaining dependencies were kept according to the Dockerfile within the NGPB repository.

\subsubsection{Comparing performance}
\label{sec:evaluation-experimental-setup-comparing-speed}
Thankfully, NGPB already prints out the time that each stage took. This is done using two helper macros called TIC() and TOC(), which are portable throughout the code base. Those rough timings are enough to show whether an optimization is faster, since the computation time for the larger molecules are way bigger than small timer randomness, or other run-to-run-variances. 

For more exact timings in the GPU specific optimizations, I profiled the kernels using Nvidia Nsight Compute, which runs kernels multiple times, eliminating variances. Additionally it provides detailed information about the utilization of resources and gives suggestions on how to optimize them. I avoided profiling the linear solvers running on the GPU by running the built in solvers like LIS.
