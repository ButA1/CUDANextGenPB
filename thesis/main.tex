\subsubsection{NGPB Parameters}
\label{sec:evaluation-experimental-setup-ngpb-parameters}

NGPB offers various different mesh types, on which the remaining mesh parameters depend \cite{nextgenpb_docs}. The first and default option being \texttt{mesh\_shape = 0} which is a de-refined mesh with a fine and coarse region, controlled by \texttt{perfil1} and \texttt{perfil2} respectively. \texttt{perfil} (short for "percentage fill") set the fraction of the fine/coarse domain size occupied by the molecule. Resolution with this mesh type is controlled through \texttt{scale}, which is equal to the inverse resolution in Ångström, meaning at a value of 2 is equal to a resolution of \texttt{0.5Å}.
% TODO not sure if I should add SI units. I won't have a lot of of units in this thesis
\texttt{mesh\_shape = 1} is a uniform cubic mesh, whose resolution isn't set by \texttt{scale}, but rather by \texttt{unilevel}. This lead to some initial confusion, and a transition to using \texttt{mesh\_shape = 0} exclusively. The remaining two types were uninteresting for my testcases.
Perfil1 is set to 0.8 by default, however the in the NGPB paper \cite{diflorio2025nextgenpb}, the authors showed that a \texttt{perfil1} of 90\%-95\% is perfectly sufficient, and would reduce the runtime significantly. I could also confirm this through my own observations. Logically, one would want the molecule to be fully inside the fine grid domain, but also leave enough room for the de-refinement transition, due to p8est restricting neighboring quadrants to be only one refinement level apart. Because of this, a \texttt{perfil1} of 1 is not feasible. \texttt{perfil2} is kept at its default value of 0.2. \texttt{scale} is also kept at its default value of 2, which was also proven to be sufficient in the paper.
Lastly, there was also the undocumented parameter \texttt{loc\_refinement}, which could basically force the mesh to be refined regardless of \texttt{mesh\_shape}, and thus route the energy calculation through the \texttt{energy} function instead of \texttt{energy\_fast}. To my surprise, this yielded worse results in my testing, and served only to test \texttt{energy\_cuda}.

\subsubsection{MPI Rank}
\label{sec:evaluation-experimental-setup-mpi-ranks}

The number of ranks for MPI is set through the \texttt{-n} or \texttt{-np}. As already explained %TODO add the chapter for distributed sparse matrices here
, the total memory consumption of all nodes increases slightly with the number of ranks, as each one needs to keep track of ghost- and halo elements. However, it can also slightly influence of the result itself, as the reduction of the individual result of the ranks may calculate in a different order. The magnitude of this error is at FP64 noise level, but can impact smaller molecules like 1CCM, where I discovered that the flux charge varied wildly with \texttt{-n}. Most local testing was performed using an \texttt{-n} of 4, while testing on the cluster was performed using an \texttt{-n} of 16.

\subsubsection{Compiler Flags}
\label{sec:evaluation-experimental-setup-compiler-flags}

Aside from the additional compiler flags added due to inclusion of CUDA, I largely used the same flags from the original makefile and \texttt{local\_settings}. Although initially I changed the optimization flag from \texttt{-o2} to \texttt{-o0} due to fears of catastrophic cancellations during floating point calculations, spawned by the \texttt{-n} discovery, it quickly proved more trouble than it was worth. It made the code extremely slow, which over-exaggerated the speedup achieved by the GPU and the need to optimize other parts of the code. I reverted back to \texttt{-o2}, but purposefully stayed away from the commented out \texttt{-Ofast -mtune=native -march=native} setting lingering inside the \texttt{local\_settings}, which would've provided even faster baseline performance, but unlike \texttt{-o2} legitimately ran the risk of altering the results significantly. Additionally, the dependencies of NGPB as also compiled using \texttt{-o2}.

\subsubsection{Testing}
\label{sec:evaluation-experimental-setup-testing}

The main two metrics used for evaluation were the execution time, accuracy of the results and also in some instances, memory usage. For this I created a handful of test cases using mostly different PQR files. Those generally fall into two categories: analytical test cases and comparative test cases. 

The analytical test cases were used to verify the correctness of the results with respect to the known analytical results taken from the NGPB paper \cite{diflorio2025nextgenpb}. Those allowed me to verify the error magnitudes independent of actually running NGPB locally, as well as the correctness of the parameters used to achieve the results from the paper. They were not used to compare speed, as they are fairly small and thus not very computationally expensive.

Comparative test cases were used to compare the results of the optimized implementation against the baseline. The baseline isn't formed by the completely unmodified version of NGPB, as the slightly altered result due to the triangulation fix is assumed to be more correct. Unlike the analytical benchmarks, these were used to compare both speed and accuracy, as they are much larger than the analytical models. 

The version of the dependencies had to be kept the static. Using NanoShaper Version 0.8 instead of the official 1.5 altered the result. Similarly, I needed switch to the unmodified version of BIMPP, sine it was partially optimized as part of this thesis in a private fork. The versions of the remaining dependencies were kept according to the Dockerfile within the NGPB repository.

\subsubsection{Comparing performance}
\label{sec:evaluation-experimental-setup-comparing-speed}
Thankfully, NGPB already prints out the time that each stage took. This is done using two helper macros called TIC() and TOC(), which are portable throughout the code base. Those rough timings are enough to show whether an optimization is faster, since the computation time for the larger molecules are way bigger than small timer randomness, or other run-to-run-variances. 

For more exact timings in the GPU specific optimizations, I profiled the kernels using Nvidia Nsight Compute, which runs kernels multiple times, eliminating variances. Additionally it provides detailed information about the utilization of resources and gives suggestions on how to optimize them. I avoided profiling the linear solvers running on the GPU by running the built in solvers like LIS.
